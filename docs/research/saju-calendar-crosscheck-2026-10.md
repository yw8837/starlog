- 절입 시각 정확도: 우리 엔진(manseryeok)의 절기표는 독립 천문 계산(astropy/IAU ERFA, JPL과 1초 이내로 일치 확인)과 **최대 32.7초** 차이다. 1929–2026년 24절기 2,352개 모두 lunar_python 값을 **가장 가까운 분으로 반올림**한 값과 정확히 같다. 즉 표를 옮기는 과정의 오류는 없고, 차이는 분 단위 반올림 때문뿐이다.

  4. 대운수 반올림: 지금은 round, 최소 1이다. floor나 ceil로 바꾸면 이번 표본 88건 중 32건 또는 37건의 대운수가 1년 달라진다.

## 2. 기준과 "같은 순간" 넣는 법

| 역할 | 라이브러리 (버전 고정) | 비고 |
|---|---|---|
| 주 기준: 절기(초 단위), 팔자, 운 | `lunar_python 1.4.8` (6tail) | GitHub에서 많이 쓰는 lunar 계열의 Python판. 절기 시각은 베이징 시각(UTC+8)이다. |
| 2차 의견: 절기, 일진, 시주 | `sxtwl 2.0.7` (寿星天文历) | Windows 휠이 cp311까지만 있어서 venv를 Python 3.11로 만들었다. |
| 민간 시각 → 순간 | Python `zoneinfo` + `tzdata 2026.5` (IANA **2026e**) | 우리 `policy.ts` 표와 독립된 데이터다. |
| 한국 음력 | `korean_lunar_calendar 0.4.0` | KASI 데이터 기반이다. lunar_python의 음력은 중국력이라 참고용으로만 썼다. |
| 독립 천문(절입 판정용) | `astropy 8.0.1` (IAU SOFA/ERFA) | 겉보기 태양 황경, 참황도. 1960년 이전은 Espenak–Meeus ΔT를 썼다. |

**독립성 주의.** manseryeok 절기표, lunar_python, sxtwl은 모두 许剑伟 寿星 계열 알고리즘에서 나왔다. 그래서 **절입 시각의 독립 검증은 astropy만** 해당한다. astropy 방법은 이전 문서(`saju-engine-eval.md` §4.1)의 JPL DE441 값 10개와 대조했고, 차이는 −0.2~−1.0초였다.

**양쪽이 시각을 다루는 방식:**

| 단계 | 우리 엔진 | 기준 |
|---|---|---|
| 입력 벽시계 → 절대 순간 | `policy.ts` 한국 연혁표(과거 표준시 + DST), 겹친 시각은 앞 시각 | IANA tzdata(`zoneinfo`), `fold=0`(앞 시각). 건너뛴 시각은 "읽을 수 있는 순간 0개"로 판정한다. |
| 연·월주 | 순간과 manseryeok 절입(분 단위)을 비교 | 같은 순간을 **UTC+8 필드로 바꿔** lunar_python에 넣는다(절입은 초 단위). sxtwl은 자체 절입 순간으로 다시 계산한다. |
| 일·시주 | 보정 시계 = 순간 + 경도×4분(KST가 아니라 지방평균시). 자시는 분리. | 같은 공식으로 만든 시계 필드를 lunar_python에 넣는다(`sect=2`: 晚子时 日柱算当天, 시간 천간은 다음 날 기준). sxtwl `getHourGZ`도 같은 규칙이다. |
| 시간 모름 | `readUnknownTime` | 같은 규칙을 Python으로 따로 구현했다. tzdata로 분 단위 스캔을 하고, 절입 시각은 lunar_python 값을 쓴다. |
| 대운 | `getLuckPillars` | lunar_python 절입(초)으로 인접 절까지 일수를 계산하고, JS `Math.round` 규칙을 적용했다. 참고로 lunar_python 자체 `getYun`(sect 1·2) 결과도 함께 기록했다. |

일·시주와 시간 모름 쪽은 관례(경도 공식, 자시 규칙)가 같으니 **구현을 검증**한 것이다. 관례를 어떻게 고를지는 §9에서 따로 다룬다. 기준 쪽이 독립적으로 제공한 것은 다음 다섯 가지다.
- 시간대 데이터
- 절입 시각
- 60갑자 일진 계산(율리우스일)
- 오호둔·오서둔 천간 규칙
- 한국 음력 데이터

## 10. 재현 방법

```powershell
# 저장소 루트에서 (첫 실행 때 .venv를 만든다. 이 PC에서는 pip 인증서 경로가 필요하다)
$env:SSL_CERT_FILE = $env:PIP_CERT = "C:\Users\Public\agent-certs\cacert.pem"
powershell -ExecutionPolicy Bypass -File scripts/crosscheck-saju/run.ps1   # 약 2분 20초. 마지막 출력이 "미분류 차이: 없음"이면 통과
```

실행 순서는 다음과 같다(`scripts/crosscheck-saju/`).
1. `gen_cases.py`: `cases.json`(100건)과 `fuzz-cases.json`(14,539건)을 만든다. 시드가 고정이라 다시 만들어도 같다.
2. `npx vitest run -c scripts/crosscheck-saju/vitest.config.ts`: `ours.crosscheck.ts`가 `computeChart`를 프로필 5개로 돌린다. 출력은 `ours.json`, `ours-fuzz.json`, `ours-lunar.json`이다. 루트 `pnpm test`에는 포함되지 않는다.
3. `reference.py`, `reference.py fuzz`: lunar_python, sxtwl, tzdata, KLC로 `ref.json`, `ref-fuzz.json`을 만든다.
4. `astro_terms.py`: astropy로 `astro_terms.json`(절기 2,352개)을 만든다.
5. `compare.py`: 위 표를 출력하고 `results.json`을 만든다. 미분류 차이가 있으면 종료 코드 1이다.

- 버전: Node 25.9.0, vitest 5.0.2, Python 3.11.15. Python 패키지는 `requirements.txt`에 고정했다.
- 두 번 연속 실행했을 때 `cases.json`, `ours.json`, `ref.json`, `astro_terms.json`, `results.json`이 바이트 단위로 같았다.
- 스윕 산출물(수십 MB)은 커밋하지 않는다(`.gitignore`).

## 11. 한계

- **KASI 공식 절기 시각과는 대조하지 못했다**(이전 문서와 같은 이유). 대신 astropy와 JPL(이전 문서)로 확인했다.
- 일·시주 경도 공식과 자시 규칙은 양쪽이 같은 관례를 쓴다. 그래서 이번 대조는 **구현**을 검증한 것이다. 관례가 맞는지는 §9의 결정 사항이다.
- 진태양시(`LAT`, 균시차), 해외 출생(도쿄·타이베이·홍콩), 1930년 이전 출생과 1908년 이전 LMT 입력은 이번 대조에 없다. 절기표 대조는 1929–2026년만 했다.
- 국내 앱 관례는 앱스토어·웹 설명 문장 기준이다. 실제 계산 결과로 확인하지 않았다.
- 1960년 이전 astropy 값은 ΔT 다항식에 의존한다(그 시기 오차는 1초 미만으로 추정). 1960–1971년은 astropy의 UTC(rubber second)를 썼다.
