# 사주(만세력) 계산 엔진 평가 — 2026-09-30

> 대상: Next.js 서버(Node 22+, TypeScript)에서 쓸 사주 4주 계산 엔진
> 방법: npm 실제 설치(정확한 버전 고정) → 같은 입력을 전 엔진에 넣어 대조 → 외부 기준(KASI·JPL)으로 판정
> 작업 공간: `%TEMP%\saju-engine-eval` (재현 스크립트: `h\*.mjs`, 아래 §10)

## 0. 결론 (TL;DR)

- **추천: `manseryeok@2.0.0`(yhj1024, MIT) + 우리 래퍼(정책 계층).** 요청한 경계 케이스에서 연·월·일주 오류가 0건이었다. KASI 음력 정본과 일치하고, 절기표는 분 단위, 한국 서머타임과 표준시 연혁 표도 들어 있다(tzdata 2026a와 대조해 일치). 의존성이 없고 1회 계산에 약 9.5µs가 든다.
- 그대로 쓰면 안 되는 이유가 있다. 기본값이 ① 서머타임 미반영, ② 경도 보정 없음, ③ 자시를 `'midnight'`(당일 천간 子시, 비주류)로 처리한다. ④ 시간 모름을 지원하지 않고(hour가 없으면 RangeError), ⑤ 서머타임 시작 때 건너뛴 없는 시각(예: 1987-05-10 02:30)도 조용히 계산한다. 그래서 **정책은 전부 래퍼가 명시적으로 주입**한다(§8).
- 사용자 기대값 중 두 개를 바로잡는다.
  - **1990 소한은 KST 23:33:14**(JPL)다. 문의에 적힌 22:33은 **중국 표준시(UTC+8) 값**이다. 그래서 1990-01-05 23:00의 월주는 **丙子**(丁丑이 아님)다.
  - **2000 입춘은 KST 21:40:23**이다. 20:00과 21:00 **둘 다 입춘 전**(己卯年 丁丑月)이다. 21:00을 庚辰으로 내는 엔진(lunar-javascript를 그대로 쓴 것, openfate, krdn)은 절기를 **1시간 일찍** 적용하는 버그가 있다.
- 탈락 사유 요약:
  - `@orrery/core`: AGPL-3.0
  - `@openfate/bazi-engine`, `@krdn/saju`, `lunar-javascript`(단독): 절기 비교가 UTC+8 기준이라 한국 출생자는 1시간 어긋남. 음력도 중국력
  - `ssaju`: 절기 최대 5분 조기, 음력이 중국식 윤달이고 `solarToLunar`가 1900-1-1을 반환하는 버그, 시간·성별 누락 시 정오·여성으로 가정
  - `@gracefullight/saju`: Node ESM import 자체가 실패, 절기 최대 6분 조기
  - `@fullstackfamily/manseryeok`: 절기를 일 단위로 처리
  - `k-saju`, `@jaeyeonling/saju`: 정확도는 좋지만 0★, 릴리스 1~3개로 성숙도 부족. **jaeyeonling은 CI 교차검증용 오라클로 채택 권장**
- `MinDaehyeon/k-saju`는 라이브러리가 아니다(SaaS 앱 저장소, HTML, 라이선스 없음). npm `k-saju`는 전혀 다른 저장소(bunhine0452)다.

### 4.5 한국 DST·표준시 연혁 표

manseryeok 내장표(`dist/time/korea-timezone.js`)를 Node 25.9 ICU tzdata **2026a**와 1908-04~1994 구간에서 30분 간격으로 대조했다.
- 전이 시점 27개가 모두 일치했다: 1948–51 DST, 1954-03-21 UTC+8:30 전환, 1955–60 DST(+9:30), 1961-08-10 UTC+9 복귀, 1987–88 DST(5월 둘째 일요일 02:00부터 10월 둘째 일요일 03:00까지).
- 불일치 25개 반시간은 **모두 시계를 되돌리는 구간(같은 시각이 두 번 있는 모호 구간)**이다. manseryeok은 이때 DST 쪽(앞 시각)으로 해석한다.
- 시계를 앞당기는 구간의 없는 시각(1987-05-10 02:30 등)은 manseryeok이 **경고 없이 계산**한다. openfate V2는 `NONEXISTENT_CIVIL_TIME`을 반환한다.

## 5. 서울 경도 보정과 균시차의 실제 크기

- 서울 126.978°E, 표준 자오선 135°E: (126.978−135)×4 = **−32.09분**(LMT).
- 균시차(EoT)는 날짜에 따라 약 −14분에서 +16분 사이다. JPL LAST(서울)로 확인한 예:
  - 2000-05-15 23:31 KST → LAST **23:02:35**. LMT만 적용하면 22:59(亥시), EoT까지 적용하면 子시라서 **시주가 바뀐다.**
  - 1988-05-10 01:30 KDT → LAST 00:01:31(5/10). LMT만 적용하면 23:58(5/9)이라 **분리 정책에서는 일주까지 바뀐다**(甲子 ↔ 乙丑).
  - 2026-09-30 00:10 KST → LAST 23:47:38(9/29).
- 따라서 “경도 보정 on/off”와 “EoT on/off”는 서로 다른 스위치로 두고, 결과마다 어떤 보정을 썼는지 남겨야 한다.

## 7. 추천

**`manseryeok@2.0.0`을 정확한 버전으로 고정(`"manseryeok": "2.0.0"`)하고, 그 위에 `sajuEngine` 래퍼를 둔다.**

- 파생 표(지장간, 12운성, 오행 집계, 신살)는 래퍼에서 **우리 표 + 버전**으로 구현한다. 해석 계층이라 학파 선택이 따른다.
- CI에는 ① 아래 골든 테스트, ② `@jaeyeonling/saju`(devDependency)와 정책을 맞춘 차등 퍼징(1900–2100 무작위 시각, 연·월·일주 비교), ③ `korean-lunar-calendar`와의 음력 전수 대조를 둔다.
- 프로젝트가 방치되면 MIT이므로 vendor한다(dist 약 195KB, 순수 TS).

## 10. 재현 방법과 한계

- 설치: `%TEMP%\saju-engine-eval`에서 `npm install --save-exact` (위 §2 버전). 실행 환경은 Node **v25.9.0**, ICU 78.2, tzdata 2026a다. **Node 22 CI에서 다시 실행이 필요하다.**
- 스크립트(`h\`):
  - `engines.mjs`: 어댑터
  - `run.mjs`: 케이스 × 엔진
  - `flip.mjs`: 월주 전환 분
  - `horizons.mjs`, `horizons2.mjs`: JPL
  - `lunar.mjs`, `sweep.mjs`, `sweep2.mjs`: 음력
  - `dstcheck.mjs`: DST 표
  - `daeun.mjs`: 대운
  - `golden.mjs`, `golden2.mjs`: 프로필별 기대값
  - `misc.mjs`: 예외와 벤치마크
  - `fixext.mjs`: gracefullight ESM 우회용(평가 전용)
- 검증하지 못한 것:
  - KASI **절기** 공식값(사이트 500, API 키 필요). 대신 JPL로 검증했다.
  - gracefullight의 Next.js 번들 동작
  - openfate·jaeyeonling의 신살·12운성 상세
  - 1908년 이전 LMT 처리의 정답
  - 인용된 KASI 1990·2000 절기값(manseryeok #16)의 원문 대조
- 자시 관법(분리 vs 통자시)과 경도 보정 기본값은 **학파·제품 결정**이다. 이 문서의 “기본”은 권장안이며, 두 설정 모두 골든을 만들어 두었다.
