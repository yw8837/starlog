## 0. 한 페이지 결론

1. 가장 안정적인 구조는 "계산(코드) -> 사실 태그 -> 사람이 쓴 룰 문장 조회 -> (선택) LLM 문장화 -> 사후 감사"이다. waylake/four-eight와 ohamma8253/samsin-saju가 이 방향이고, 나머지 대다수는 LLM에 생년월일이나 요약 몇 줄만 주고 십성·대운·용신까지 알아서 하게 둔다. 후자는 명식 자체가 틀리거나 섹션끼리 어긋난다.
2. 시간 모름은 "삼주 + 시주에 의존하는 주장 차단 + 한계 표시"가 정답이다. 실제 구현에서는 12시 기본값(ssaju), 정오 가정(chatju-premium), 0시로 대체(drsaju), 12시=모름 센티널(dasilver1812)처럼 조용히 값을 채우는 버그가 흔하다.
3. 사실로 말해도 되는 것은 계산과 정의뿐이다. 신강/신약, 용신, 격국, 조후 처방, 합화 성립, 신살, 공망의 의미는 엔진마다 결과가 갈린다. 여러 프로젝트(saju-agent, MinDaehyeon/k-saju, jeomsin-fortune-reader, openfate-ai/bazi-engine, yhj1024/manseryeok)가 스스로 "단순화/미반영/미판정"이라고 적어 두었다.
4. 흔한 품질 실패: 바넘형 템플릿, Math.random/해시로 만든 점수·금액·백분율, 건강·결혼시기·투자 단정, 무료와 유료 결과 불일치(jake-liner), API 실패 시 조용한 범용 문구 대체(DEOKHOKANG/sajuwooju), 연월주 계산 오류(idol-saju-mate는 양력 1월을 寅월로 처리).
5. 우리 샘플: 명식 사실(연월일주, 지장간, 십성, 오행 수, 대운 방향, 현재 대운)은 전부 재현·일치했다. 고칠 곳은 (a) 바넘형 문장 5~8개, (b) 조후 문장 1개의 단정, (c) 대운 지지(辰)와 2026년 6월 전후 전·후반 경계 누락, (d) 시간 모름의 영향 과소 서술(자시 경계에서는 일간도 바뀔 수 있음), (e) JSON에 신강약·12운성·합충·세운·출처 필드가 없음, (f) `lunar-javascript`는 절기를 UTC+8로 내므로 KST 입력을 그대로 넣으면 입춘 등 절입 전후 1시간에서 연·월주가 틀릴 수 있음이다.

## 2. 서비스들이 리딩을 만드는 방식 (L0~L4)

| 유형 | 내용 | 해당 저장소 | 평가 |
|---|---|---|---|
| L0 | 생년월일(시)을 LLM에 그대로 주고 명식도 산출하게 함 | SajuGist, keypeet, kimhyunho220972(계산 과정 표기·교차검증 권고는 함), DEOKHOKANG | 명식이 틀려도 검출 불가. 같은 입력의 재현성 없음 |
| L0' | 가짜/스텁/부정확한 "계산" | ClarenceCHL(모든 사용자에게 같은 하드코딩 명식 반환), dasilver1812(연·월·일 나머지 연산), idol-saju-mate(달력 연도·달력 월을 연주·월주로 사용) | 명식부터 무효 |
| L1 | 계산 후 요약 필드만 전달 | drsaju(4기둥+오행 개수만), saju-paljja, chatju v1 | 십신·대운·용신을 LLM이 임의로 만듦. drsaju는 프롬프트가 십신 분석과 대운 분석을 요구하지만 그 데이터를 주지 않음 |
| L2 | 계산 후 풍부한 사실표 전달 | ssaju(`toCompact` 약 950토큰), myungri-rx, saju-agent, hoonsikim, chatju v2, rkdtndls k-saju | 사실 오류는 줄지만 "어떤 문장이 어떤 근거에서 나왔는지"는 못 봄 |
| L3 | 계산 -> 사실 태그 -> 큐레이션 룰 조회 -> (선택) LLM 문장화 | four-eight, MinDaehyeon k-saju(결정론 본문 위에 LLM은 사실을 바꾸지 않고 재서술, 결과 캐시) | 근거 추적 가능. 룰 문장을 사람이 써야 함 |
| L4 | L3 + 주장 계획(ClaimPlan)·증거 ID + 사후 감사 | samsin-saju(증거 ID 없으면 문장 없음, 렌더 후 금지어·과장·근거 누락 검사), XiaoChu(톤 블랙리스트를 저장 전에 코드로 차단) | 가장 엄격. 개발비 큼 |

four-eight가 밝힌 설계 이유가 참고할 만하다. 모델이 산술(육십갑자, 절기 비교)을 그럴듯하게 틀린다는 점, 근거 조회를 벡터 검색이 아닌 태그 정확 일치로 한 이유(닫힌 온톨로지라 "편재를 찾는데 정재가 딸려 오는" 오류를 막음), 기준선 문장이 항상 존재하고 AI 문장은 요청 시에만 생성한다는 점이다.

우리 권장은 L3를 기본으로 하고 L4의 일부(문장별 claimId·evidenceId, 금지어·수치·시간 의존 검사)만 가져오는 것이다(9장).

무료/유료 분업의 실제 사례: hoonsikim은 무료를 룰 기반(LLM 호출 없음, 즉시), 유료를 LLM 장문(한국어 6,000~10,000자, 5섹션+마무리)으로 나눴다. four-eight와 k-saju는 결정론 본문을 먼저 두고 LLM이 그 위를 다듬는다. 무료와 유료가 같은 사실 집합을 공유해야 불일치가 안 난다(7장 F9).

## 8. 권장안 A - 리딩 구조 (무료 티저 / 유료 프롤로그 / 주제 리딩)

### 8.1 설계 원칙

1. 문단 하나는 "명식 근거 -> 일상 장면 -> 작은 실험" 순으로 쓴다. 근거 없는 형용사 나열은 쓰지 않는다.
2. 무료와 유료는 같은 주장(claim) 집합의 부분집합이다. 유료는 깊이, 범위, 근거 공개를 판다. "숨겨 둔 나쁜 소식"을 파는 구조로 만들지 않는다.
3. 미래와 사건은 단정하지 않고 "국면" 언어로만 말한다. 대운·세운은 기운의 성격을 서술하고, 좋고 나쁨의 등급을 매기지 않는다.
4. 리딩 안에 사용자 확인 문장을 1~2개 둔다("이런 경험이 있다면 이 구조와 맞물려 읽을 수 있어요"). XiaoChu가 명식 검증에 체감·과거 사실을 쓰는 방식을 문장 수준으로 축소한 것이다. 맞았는지 틀렸는지 피드백 버튼을 달면 품질 측정 데이터도 얻는다.
5. 영역(성격/연애/일/재물/올해)마다 근거 축과 문장을 분리한다. 같은 명식 특징도 영역마다 다른 행동 장면으로 번역한다.
6. 시간 모름은 별도 변형본을 만든다(8.5).

### 8.5 시간 모름 변형

- 0장에 조건을 드러내고, 시주 의존 주제(자녀·말년·정밀 시기)는 잠그지 말고 아예 제공하지 않는다.
- 3장 십성 축은 시주를 뺀 위치만 쓴다. 6장 대운 시작 시점은 범위로 표기한다(부록 A: 시간 모름의 영향은 약 2개월).
- 7장에 "밤 11시~새벽 1시 반 사이에 태어났다면 일간이 달라질 수 있다"와 확인 질문을 넣는다(부록 A).
- 시각을 알게 되면 같은 claim 집합을 다시 계산한다는 재계산 경로를 제품 정책(횟수·가격)과 함께 명시한다.

### 8.6 무료에서 유료로

잠금 목차는 "무엇을 더 볼 수 있는가"(근거 축)를 보여 주고, 결과를 감추지 않는다. 문장 중간 절단과 "주의해야 할 시기도 보여요" 식의 은닉 예고(myungri-rx)는 쓰지 않는다. 무료와 유료의 수치·사실은 같은 FactSet 해시에서 나와야 한다(F9).

## 9. 권장안 B - 프롬프트·데이터 계약

### 9.1 파이프라인

입력 정규화(시간 정책 확정) -> 계산(코드, 골든 검증 통과 엔진) -> FactSet(JSON) -> 사실 태그 -> 룰 조회(우리가 쓴 룰 문장) -> ClaimPlan(주장·강도·근거 ID) -> LLM 문장화(JSON 출력) -> 감사(코드) -> 캐시(키 = 명식 해시 + 룰 버전 + 프롬프트 버전 + 모델).

LLM 없이도 룰 원문을 이어 붙인 기준선 문장이 항상 존재해야 한다(four-eight). 감사에 실패하면 범용 문구가 아니라 이 기준선 문장으로 대체하고, 그렇게 표시한다.

### 9.3 시스템 프롬프트 골격 (우리 문장으로 새로 작성한 초안)

```
역할: 명리 해설가. 아래 [사실]과 [근거]에 있는 내용만으로 풀이한다.

규칙
1. 새 간지, 십성, 신살, 관계, 나이, 연도, 개수를 만들지 않는다. 표기는 [사실]의 display를 그대로 복사한다.
2. [사실]에 없는 질문(건강 진단, 결혼·이별 시기, 투자, 소송, 수명 등)은 "이 풀이의 근거로는 말하기 어렵다"고만 답한다.
3. limits에 코드가 있으면 그 한계 문장을 반드시 포함하고, timeKnown=false면 시주에 의존하는 문장을 쓰지 않는다.
4. 모든 문단은 claimPlan의 claimId를 1개 이상 인용하고, claimPlan에 없는 주장은 쓰지 않는다.
5. 어미는 claim 강도에 맞춘다. strong: "~로 읽어요". moderate: "~한 편으로 읽어요", "~하기 쉬워요". weak: "~한 국면이에요", "~를 살펴볼 만해요".
6. 좋은/나쁜 시기·해·달·운이라고 등급을 매기지 않는다. 어떤 성격의 기운이 실리는지만 서술한다.
7. 문단은 "명식 근거 -> 일상 장면 1개 -> (있으면) 작은 실험" 순서. 약점은 스스로 조절할 수 있는 행동과 함께 쓴다.
```
