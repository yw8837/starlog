## 1. 한 줄 정의

**카드 10장으로 깊게 보는 심층 타로(5,900원), 사주와 타로로 두 사람을 함께 보는 우리 사이 궁합(9,900원), 사주로 미리 보는 2027 신년운세(9,900원)**를 판다. 세 상품 모두 계산된 사실(서버가 뽑은 카드, 서버가 계산한 명식) 위에서만 풀이하고, 긴 풀이는 2~3개 파트로 나눠 파트마다 검증하며 240초 예산 안에서 만든다. 돈은 P4 규칙 그대로 **완성되어 저장될 때만** 나간다.

## 2. 범위

### P5에 넣는다

- 세 상품의 생성기(프롬프트, 구조화 출력 스키마, 검증기, 모의 출력), 파트 단위 생성과 이어 쓰기(재개) 토큰
- 궁합·신년운세의 계산 사실: 두 명식의 관계(일간, 오행 보완, 기둥 사이 합·충, 대운이 겹치는 때), 2027 정미년 세운과 12개월 월건
- 카드 10장 배열과 5장 관계 배열(뽑기는 기존 부채꼴 뽑기 화면 재사용, 카드는 서버가 정함)
- 무료 미리보기(전자상거래법 제17조 제2항 제5호의 시험 사용) 세 가지
- P4 카탈로그의 프리미엄 상품을 판매 가능으로 바꾸고 판매 플래그 `STARLOG_PREMIUM`로 연다
- 이어서 물어보기(프리미엄은 5번), 계정·기기 보관, 내 기록·장 화면
- 공유 이미지(P3 `next/og` 방식), 상품 소개 페이지 3개(SEO), 샘플 페이지 3개(noindex, 토스 심사·가격 안내용)
- 개인정보처리방침·약관·환불 안내 개정(상대방 정보, 판매 기간)
- 품질 평가: 골든 입력, 블라인드 판정 기준, 실제 API 스모크 예산과 통과 기준
- 실행 안내서(`docs/runbook-premium.md`)

### P5에서 뺀다

- 별조각·베타 무료로 프리미엄 열기(결제 전용, 운영자 패스만 예외)
- 궁합 점수·퍼센트, 다인 궁합(3인 이상), PDF 내보내기
- 2028 신년운세(같은 구조로 다음 해에 상품만 추가)
- 프리미엄 풀이를 다른 풀이의 "지난 풀이" 자료로 쓰기(궁합은 상대 정보 때문에 제외, 나머지도 단순하게 제외)

## 4. 의존성과 경계

### P4(계정·결제)와 같이 쓰는 것 — 새로 만들지 않는다

| P4가 만든 것 | P5에서 쓰는 방식 |
|---|---|
| `lib/pay/catalog.ts` `PRODUCTS`, `sellable()` | 프리미엄 세 상품의 `deliverable`을 `true`로 바꾸고, `closesAt`(판매 종료)을 더한다. 열기·닫기 시각은 `SITE.price.premium`에 둔다(한 곳) |
| `POST /api/pay/orders`, 결제 화면, 승인, 웹훅, 환불 | 그대로. 주문 생성에 "프리미엄은 `STARLOG_PREMIUM`이 열렸을 때만" 조건 하나를 더한다(409 `NOT_AVAILABLE`) |
| `credit_lots.product_id`(용도 지정 로트), `reserveUnlock`, `deliverUnlock`, `releaseUnlock`, 예약 6분 | 프리미엄 열기 = 그 상품에 묶인 유료 로트 1단위 예약. `reserveUnlock`에 **용도 지정 로트만** 쓰는 옵션을 더한다(나중에 생길 달빛 묶음 로트가 9,900원 상품을 1단위로 여는 일을 막음). 여러 요청에 걸친 생성을 위해 `extendUnlock`(예약 연장)을 더한다 |
| `lib/api/stream.ts`의 `Settlement`(전달 전 저장·차감, 실패 시 복구), `credit` 비용 분리 | 그대로 쓴다. 파트가 남은 응답(`continue`)에서는 저장 대신 예약을 연장한다 |
| `readings` 테이블(암호화 보관), `insertReadingStatement` | 그대로 쓰되 `kind` CHECK에 프리미엄 세 종류를 더하는 마이그레이션(`0003_premium_readings.sql`, 표 재구성)을 둔다 |
| 이어서 물어보기의 계정 사본 기록(`readingId`) | 그대로 |
| `UnlockSheet`·`useAccount`·`loginHref`·`checkoutHref` | 프리미엄 미리보기 화면의 열기 패널에서 쓴다. `checkoutHref`의 상품 타입을 넓힌다 |
| 내 정보 "결제한 풀이" | 프리미엄 상품의 `열기` 링크를 각 상품 흐름으로 잇는다 |

P5는 P4 Task 1~17이 병합된 뒤에 시작한다(P5 Task 0이 확인). 지금 작업 트리에는 `lib/pay/`가 아직 없다.

### P3(별자리 인연)와 같이 쓰는 것

- 공유 이미지: P3 Task 10의 `lib/og/googleFont.ts`, `components/ui/ShareImageButton.tsx`, `app/api/og/*` 방식. P5는 `app/api/og/premium/route.tsx` 하나를 더한다. P3 Task 10이 병합되기 전에는 P5의 공유 작업(Task 23)만 기다린다.
- D1 마이그레이션 번호: P3 `0001`, P4 `0002`, P5 `0003`(구현 시점에 다음 빈 번호).

### Task A(모델 블라인드)

- 하드 검증기 `modelNameViolations(draft, out)`(`lib/ai/validate.ts`)와 프롬프트 규칙 `MODEL_BLIND_RULE`(`lib/ai/style.ts`). 프리미엄 검증기는 모두 첫 줄에서 이것을 부르고, 프리미엄 시스템 프롬프트에는 `MODEL_BLIND_RULE`를 넣는다(Task A 확인, 2026-10-01).

### P2b(생성 경로)

- 스트리밍 프로토콜(NDJSON `start/section/retry/ping/done/error`), 240초 생성 예산, 서버 쪽 지출 집계, 문체 규칙과 AI 티 점수는 그대로다. 프리미엄은 **한 요청에 한 파트**를 만들기 때문에 새 이벤트 종류가 필요 없다(6절).

## 5. 상품별 설계

### 5.1 심층 타로 · 카드 10장 (5,900원)

**흐름**
1. 상품 페이지 `/premium/deep-tarot` → `카드 10장 뽑으러 가기` → 기존 질문 만들기(`/tarot/new?spread=deep`, 누구·무엇·언제) → 상황 고르기 → 카드 뽑기(부채꼴에서 10장).
2. 카드 뽑기는 기존 `DrawStage`를 쓴다. 자리 칸은 10개(2줄 5칸). 서버 `/api/tarot/draw`가 템플릿 `deep-tarot`으로 10장을 정하고 drawToken을 준다.
3. `/premium/deep-tarot/result`: 무료 미리보기(아래) + 열기 패널. 결제(P4) 뒤 돌아오면 바로 생성을 시작한다.
4. 생성이 끝나면 기기와 계정에 저장하고 장 화면(`/chapter/<id>`)으로 간다.

**자리와 읽는 렌즈**(코드가 가진 문구, 프롬프트에 그대로 들어감)

| # | 자리 | 렌즈 |
|---|---|---|
| 1 | 지금의 나 | 이 질문의 한가운데에서 지금 내가 놓인 자리 |
| 2 | 가로막는 것 | 지금의 나를 가로지르며 막거나 시험하는 것 |
| 3 | 바탕 | 지금 상황 밑에 깔린 뿌리 |
| 4 | 지나온 것 | 막 지나왔거나 지나가고 있는 일 |
| 5 | 바라는 것 | 내가 의식적으로 바라거나 목표로 삼는 것 |
| 6 | 다가올 것 | 가까운 시기에 다가올 흐름 |
| 7 | 나의 태도 | 이 일을 대하는 나의 태도 |
| 8 | 주변 | 주변 사람과 환경의 분위기(다른 사람의 속마음이 아니라 분위기) |
| 9 | 바람과 걱정 | 마음속에서 바라면서도 걱정하는 것 |
| 10 | 결과의 방향 | 지금 흐름이 이어질 때 닿는 방향(정해진 결말이 아님) |

KB에는 새 자리의 `positionHints`가 없다. `content/kb/cards/_index.json`의 `positionFallback`에 열 자리를 더한다(바라는 것·바람과 걱정 → `나의 마음`, 주변 → 주제 `group`, 나머지 → 주제 `self`).

**풀이 구조(코드가 소제목을 가짐, 잠긴 목차와 1:1)**

| 절 | 소제목 | 분량(공백 제외) |
|---|---|---|
| 한 줄 결론 | 한 줄 결론 | 60자 이하 |
| 자리별 10절 | `<자리> · <카드 이름>` | 절마다 260~340자 |
| 교차 | 지금의 나와 가로막는 것 | 350~450자 |
| 두 갈래 | 두 갈래로 이어 읽기(세로: 바탕→지금→바라는 것, 가로: 지나온 것→지금→다가올 것) | 갈래마다 220~300자 |
| 기둥 | 나와 주변, 그리고 결과의 방향(7~10) | 380~500자 |
| 시기 | `<시기>, 언제 움직이면 좋을지`(기존 규칙) | 150~250자 |
| 행동 | 오늘 해볼 작은 행동 | 80~160자 |
| 관찰 | 며칠 안에 확인해 볼 신호 | 80~180자 |
| 이어서 물어볼 질문 | (목록) | 2개, 각 30자 이하 |

합계 약 4,500~5,500자(목표 5,000자). 검증은 기존과 같이 ±25%.

**생성 파트**
- 파트 A(약 3,000자): 한 줄 결론 + 자리별 10절. 입력은 템플릿·사용자 자료·10장 카드 KB.
- 파트 B(약 2,000자): 교차·두 갈래·기둥·시기·행동·관찰·질문. 입력은 같은 자료 + 파트 A의 요약(코드가 만든 "자리별 첫 문장")으로 같은 말을 되풀이하지 않게 한다.

**검증(하드)**: 모델 이름, "켈틱/셀틱/celtic", 기존 타로 금지어·바넘·타인 마음 단정·날짜 지정·주제 이탈·없는 카드 이름, 자리·카드 그대로 복사, 자리별 절마다 그 카드의 그림 사실 인용, 역방향 카드는 역방향으로 읽음, 그림 오묘사, 교차 절은 1·2번 카드를 모두 이름으로, 두 갈래는 각 갈래의 카드 세 장 가운데 두 장 이상을, 기둥은 7~10번 가운데 세 장 이상을 이름으로 부름, 칩·메모 반영, 분량. 소프트(3개 이상일 때만 재생성): AI 티, 행동 동사 반복, 칩 되풀이, 카드를 주어로 세운 문장 6번 초과.

**무료 미리보기**: 10장 모두 앞면과 자리 이름, 자리마다 한 줄 키워드(코드가 KB의 정·역 핵심어에서 고름, AI 비용 없음), `지금의 나` 한 문단 300~400자(AI, 1번 카드 KB만 입력), 잠긴 목차. 맛보기 하루 횟수(5번)와 같은 한도를 쓴다. 유료 본문의 `지금의 나` 절은 무료 문단과 다른 그림 사실·다른 각도로 쓴다(상위 설계 15절).

### 5.2 우리 사이 궁합 · 사주 + 타로 (9,900원)

**입력**
- 나: 이 기기에 저장된 사주 정보(`starlog.saju-profile`)를 확인 화면으로 보여 주고 고칠 수 있게 한다. 없으면 기존 사주 입력 양식. 연애·일 상태는 선택.
- 상대: 양력·음력(윤달), 생년월일, 태어난 시각(모름 가능), 성별(대운 방향용), 부르는 말(선택, 10자 이하, 예: "민지", "팀장님"). 출생 지역은 묻지 않고 서울 경도로 계산한다(시각을 알 때만 영향, 기본값 6).

## 6. 공통 생성 구조

### 6.1 한 요청에 한 파트, 봉인한 이어 쓰기 토큰

측정(Opus 5.5, medium, 2026-09-30 스모크 5회): 표준 타로 전체 풀이 63초·출력 6,360토큰, 사주 프롤로그 94초·출력 10,038토큰. 출력 속도는 초당 약 100토큰, 출력 토큰은 본문 한 글자당 약 3.2~3.35개(생각 포함). 신년운세를 한 번에 만들면 약 230초라 240초 예산을 넘기 쉽고, 재생성 여유가 없다.

그래서:
1. 각 상품은 정해진 파트 목록을 가진다(심층 타로 2, 궁합 2, 신년운세 3). **한 HTTP 요청은 다음 파트 하나만** 만들고 검증한다. 파트 하나는 약 66~101초라 한 번의 재생성까지 240초 안에 들어간다.
2. 마지막이 아닌 파트가 검증을 통과하면 응답의 `done` 데이터가 `{status: "continue", resume, done: k, of: n}`이다. `resume`은 서버가 봉인한(AES-GCM) **이어 쓰기 토큰**으로, 지금까지 검증된 파트, 사용자(또는 운영자) 식별, 입력의 키 해시, 예약 id, 만료(24시간)를 담는다. 클라이언트는 내용을 읽을 수 없다.
3. 클라이언트는 같은 입력과 `resume`으로 곧바로 다시 요청한다. 서버는 토큰을 열어 사용자·입력이 같은지 확인하고 다음 파트를 만든다.
4. 마지막 파트가 통과하면 서버가 파트를 합쳐 완성본을 만들고, 장 토큰을 발급하고, P4 `Settlement.deliver`로 계정에 저장하고 차감한 뒤 `{status: "done", reading, chapterToken, readingId}`를 보낸다.
5. **서버에는 중간 결과를 저장하지 않는다.** 파트는 봉인 토큰 안에서만 클라이언트(탭의 sessionStorage)에 머문다. 이것이 "상대 정보는 따로 저장하지 않는다"를 지키는 방법이다.
6. 텍스트는 완성 전까지 화면에 보내지 않는다(스트리밍 프로토콜: 검증 전 텍스트를 보내지 않음, P4: 전달 전 차감 없음). 진행 표시만 `section` 이벤트로 한다.

**재개(resume-safe)**: 파트 k에서 실패하면(생성 오류, 품질 실패, 240초 초과, 연결 끊김) 그 요청의 예약은 P4대로 복구된다. 클라이언트에는 직전 `continue`의 토큰이 남아 있어 `이어서 쓰기`를 누르면 파트 k부터 다시 만든다. 이미 검증된 파트는 다시 생성하지 않는다(비용과 시간 절약). 탭을 닫으면 토큰도 사라지고, 결제한 풀이는 남아 처음부터 다시 연다.

**진행 표시**: 파트마다 소제목 키가 겹치지 않게 스키마를 짠다(예: 신년운세 B의 `firstHalf`, C의 `secondHalf`). 화면은 `2/3 · 4월을 적고 있어요`처럼 파트 번호와 단계를 보인다. 예상 시간(심층 타로 약 3분, 궁합 약 3분, 신년운세 약 4분)을 미리 말한다. 문구는 "창을 닫지 말아 주세요. 닫으면 처음부터 다시 써요."

### 6.2 프롬프트와 캐시

- 시스템 프롬프트는 상품·파트 계열별로 고정 문자열(캐시)이다: `DEEP_TAROT_SYSTEM`(기존 타로 규칙 + 심층 형식), `MATCH_SAJU_SYSTEM`(궁합 사주 파트), `MATCH_TAROT_SYSTEM`(궁합 카드 파트), `NEWYEAR_SYSTEM`(기존 사주 규칙 + 신년 형식). 기존 `TAROT_SYSTEM`, `SAJU_SYSTEM`은 바이트까지 그대로 둔다(규칙 부분을 `TAROT_RULES`, `SAJU_RULES`로 꺼내 재조합하고, 같은 문자열임을 테스트로 고정).
- 모든 프리미엄 시스템 프롬프트에 `STYLE_RULES`, `MODEL_BLIND_RULE`, 그리고 "이 풀이를 다른 이름의 전통 배열로 부르지 않는다"는 줄을 넣는다.
- 같은 상품의 파트들이 함께 쓰는 사용자 자료(카드 KB, 명식 사실)는 사용자 메시지의 **첫 블록**에 두고 `cache_control`을 붙인다(`GenerationTask.shared`). 다음 파트가 5분 안에 이어지므로 캐시 읽기($0.2/M)로 들어간다. Opus 5.5의 최소 캐시 길이는 512토큰(claude-api 문서)이라 모두 넘는다.
- 모델·effort: Opus 5.5, `medium`(표준 전체 풀이와 같음). 환경 변수로 상품별 변경(`STARLOG_MODEL_PREMIUM_DEEP`, `STARLOG_EFFORT_PREMIUM_NEWYEAR` 등). 평가에서 `high`와 비교한다(12절).

### 6.3 이어서 물어보기 (프리미엄 공통)

- 5번(심층 타로는 소유자 결정, 궁합·신년은 기본값 11). 장 토큰 유효기간 30일(기본값 12).
- 결제한 풀이의 물어보기는 베타의 하루 물어보기 쿠키 한도를 쓰지 않는다. 장별 서버 집계(기존 `turns:<chapterId>`)와 IP 제한은 그대로다. 비용은 `cost.paid`로 따로 기록한다.
- 비용을 줄이려고 풀이 전체 대신 **요약 + 관련 절 원문**을 넣는다: 모든 절의 소제목과 첫 문장, 그리고 질문에 나온 자리 이름·달("3월")·영역("돈") 같은 말과 소제목이 겹치는 절 최대 2개의 원문.

## 7. 결제·원장·환불 (P4 그대로, 다른 점만)

- 여는 방법은 `paid`(로그인 + 그 상품에 묶인 쓰지 않은 유료 로트)와 `owner`(운영자 패스, QA) 둘뿐이다. `free`(별조각)와 `beta`는 프리미엄에서 400 `BAD_REQUEST`.
- 예약: 첫 요청에서 1단위 예약(6분). `continue`로 끝나는 요청과 다음 파트 요청의 시작에서 `extendUnlock`으로 6분씩 연장한다. 연장할 예약이 이미 풀렸으면(실패 뒤 재개) 새로 예약한다. 쓸 수 있는 로트가 없으면 402 `NO_CREDIT`.
- 전달·차감: 마지막 파트가 검증된 뒤 P4 `Settlement.deliver`(계정 저장 + `deliverUnlock` 한 batch). 실패는 `release`.
- 판매가 꺼져도(플래그 off, 판매 기간 종료) **이미 산 풀이는 언제든 연다**(P4 원칙). 미리보기도 그 상품의 쓰지 않은 결제가 있으면 열린다.
- 환불: P4 그대로(쓰지 않은 결제는 언제든 버튼 하나로 전액, 완성되어 저장된 뒤에는 청약철회 제한). 실패 화면: "풀이를 다 적지 못했어요. 결제한 풀이는 그대로 남아 있어요." 주 버튼 `이어서 쓰기`(토큰이 있으면) 또는 `다시 열기`, 보조 `환불받기`.
- 결제 화면의 범위 3줄(P4 `scopeLines`)에 프리미엄 상품 문구를 더한다: 예) 심층 타로 "카드 10장 풀이 전체 · 약 5,000자", "이어서 물어보기 5번", "이 기기와 계정에 보관".

## 8. 판매 플래그

| 이름 | 값 | 뜻 |
|---|---|---|
| `STARLOG_PREMIUM` | `off`(기본) / `owner` / `on` | 프리미엄 새 주문과 미리보기를 누구에게 여는가. `STARLOG_PAYMENTS`가 판매를 연 상태여야 한다(`salesOpen`). 이미 산 풀이를 여는 것은 막지 않는다 |
| 판매 기간 | `SITE.price.premium[].opensAt`, `closesAt` | 신년운세만 있음(5.3) |

`GET /api/premium/status` → `{products: [{id, open, opensAt, closesAt}]}`(기기별, 운영자 쿠키 반영, D1 없음). 상품 페이지와 가격 페이지의 버튼·배지가 이것을 읽는다. 페이지 본문(가격, 범위)은 정적이라 검색에 그대로 보인다.

## 9. 개인정보 (상대방 정보)

## 12. 품질 평가 (열기 전에 반드시)

**골든 입력(상품마다 6개, `content/eval/premium/golden.json`)**
- 심층 타로: 연애·연락(관계 주제), 이직·일, 돈·지출, 갈등·화해, 직접 쓴 주제, 역방향 5장 이상.
- 궁합: 연인(둘 다 시각 앎), 썸(상대 시각 모름), 부부(일지 충), 친구(같은 일간), 동료(오행 한쪽 몰림), 가족(대운이 2년 안에 바뀜).
- 신년운세: 시각 앎·직장인·고민 있음, 시각 모름, 2027년에 대운이 바뀜, 입춘 근처 출생, 음력 윤달 출생, 구직·고민 없음.
- 카드는 시드로 고정(같은 입력이면 같은 카드)해 A/B를 같은 조건에서 비교한다.

**블라인드 판정 기준(10개, 각 1~5점, 50점 만점, `content/eval/premium/judge-rubric.md`)**: 개인화(입력이 문장마다 보이는가) / 근거(카드 그림·명식 사실에 기대는가) / 주제 적합 / 실용(바로 할 수 있는 행동) / 안전(단정·공포·타인 마음·보장 없음) / 문장(AI 티, 번역투, 반복 없음) / 깊이(뻔하지 않은 통찰) / 구조(파트 사이 일관, 되풀이 없음) / 시기 구체성(달·국면·조건) / 가치(이 가격에 다시 사겠는가). 판정자는 별도 에이전트(Opus)로, 쌍 파일만 보고 어느 쪽이 우리인지 모른다(기존 `content/eval/ab-2026-09-30/judge.md` 방식).

**비교 대상**
- 우리끼리: 프롬프트 판본 A/B, effort `medium` vs `high`(상품마다 3개 입력).
- 경쟁 서비스: `content/eval/competitors/`의 캡처(포스텔러 신년운세·AI 상담소, 헬로우봇 신년운세 구성, 점신 신년운세, 사주아이 궁합). 카드 10장 경쟁 캡처는 없다(막힘 16절). 캡처가 부분뿐이라 같은 분량으로 잘라 비교한다.

**통과 기준(상품마다)**
1. 골든 6개 모두 완성(`QUALITY` 실패 0), 파트당 평균 시도 1.3 이하.
2. 판정 평균 40/50 이상, 안전 항목은 모두 5, 어떤 항목도 평균 3.5 미만이 아님.
3. 경쟁 캡처와의 쌍에서 이기거나 비김 80% 이상.
4. 실측 AI 비용(풀이 + 물어보기 2회) 가격의 12% 이하, 아니면 소유자 승인.
5. 파트 시간 p95 150초 이하.
6. 소유자가 상품마다 샘플 하나를 읽고 승인 → 그 출력이 샘플 페이지가 된다.

**스모크 예산(실제 API)**: 한 바퀴(상품 3개 × 입력 6개, 풀이 + 미리보기 + 물어보기 2회) 약 16,000원. 바퀴 3번 + effort 비교 약 9,000원 + 샘플 다시 만들기 약 3,000원 ≈ 60,000원. **상한 70,000원**(약 $47). 스크립트가 누적 추정 비용이 바퀴 예산(`SMOKE_BUDGET_KRW`, 기본 20,000원)을 넘으면 새 호출을 시작하지 않는다.

1. 어둡게 배포: P5 병합 → D1 원격 마이그레이션 `0003` → 배포. `STARLOG_PREMIUM=off`. 상품 페이지·샘플만 보이고 버튼은 `준비 중`.

- 단위: 계산 사실(엔진과 대조한 2027 월건·입춘, 두 명식의 합·충·보완), 프롬프트 조립(규칙 포함, 사용자 글은 태그 안), 스키마, 검증기(위반 예시가 걸리고 모의 출력은 통과), 이어 쓰기 토큰(위조·다른 사용자·다른 입력·만료 거부), 파트 실행기, 예약 연장, 마이그레이션.

- e2e(Playwright, 모의 AI·결제·카카오): 상품 페이지 → 흐름 → 결제 → 생성(여러 요청) → 장 화면 → 물어보기, 세 상품.
